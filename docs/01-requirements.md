# 01 需求、范围与成功标准

## 用户与业务目标

本项目面向询问制度或产品问题的员工，目标是在有限资料中找到可核对的答案，而不是根据常识补写企业政策。需求依据为仓库根目录的《考核规则.md》和《项目要求.md》；原始要求保留，不用实现结果反向修改验收标准。

输入为一个问题及可选的 `user`/`assistant` 对话历史。知识库只使用合成制度和 FAQ，每篇包含文档 ID、版本日期、适用范围、优先级及带 ID 的原文片段。未知的适用范围、优先级明确记为 `null`。

输出必须同时包含：

- `answer`：答案，或无法可靠回答的说明。
- `citations`：文档 ID、片段 ID、版本日期、原文引用。
- `gaps`：资料缺口、未完成原因。
- `status`：`answered`、`needs_clarification`、`insufficient_evidence` 或 `incomplete`。
- `clarification_question`：需要追问时给出具体问题，否则为空字符串。

## 本次实现范围

- Python 3.9 及以上的 CLI；通过标准库实现，无第三方包依赖。
- 单 Agent：模型选择 JSON 动作，执行本地工具，观察返回，再选择动作或结束。
- 两个只读工具：文档检索和原文片段读取。
- 真实模型与离线 Mock 明确分开；真实模式失败不会自动降级成 Mock。
- 有界决策、参数校验、引用校验、结构化错误和可复核 Trace。
- 可执行单元测试、固定合成验收样本、文档变更和故障注入测试。

不在范围内：图形界面、线上部署、多 Agent 应用、向量数据库、完整企业权限模型、生产级 Runtime、真实企业数据接入和统计意义上的泛化能力证明。开发过程中使用多个 AI 协作角色，不意味着交付的应用是多 Agent。

## 动态决策要求

真实模式不能用固定的 `if D01 and D02` 分支输出业务结论。模型应根据每轮观察选择补充检索、读取原文、追问或停止。执行引擎只负责预算、动作分发、格式及来源校验。

冲突场景中，D01 为 30 天、D02 为 15 天，且没有适用范围和优先级。成功行为应读取双方原文并查证消歧依据；仍无法确定时列出双方引用并请求确认。不能自动选择更短期限，也不能把较新的版本日期视为优先级。

至少保留两种真实执行路径，并能从 Trace 核对模型看到的工具结果与后续动作。规则驱动 Mock 仅证明接口和流程可运行，不作为 ReAct 决策达标证据。

## 验收映射

具体输入及程序可检查的预期保存在 `data/cases.json`。下表是目标，不是测试通过声明；实际结果统一见 `docs/03-evaluation.md`。

| 验收要求 | 用例 | 预期行为 |
|---|---|---|
| 明确答案 | T01 | 只有 D01 时根据原文回答 30 天并引用 D01 |
| 文档冲突 | T02 | 读取 D01/D02，补充查证，列出 30/15 天冲突并追问 |
| 资料外问题 | T03 | 停车位申请无资料依据时说明资料不足，不借常识编造 |
| 改写后的相似问题 | T04 | 改写问题仍取得相关资料，结论与 T01 一致 |
| 上下文追问 | T05 | 理解“那期限呢？”指向报销，并重新获取本轮证据 |
| 工具失败：可恢复 | T06 | 观察一次检索失败，选择合理恢复动作并取得证据 |
| 工具失败：持续失败 | T07 | 不无限重试，不把工具故障说成资料不存在；明确未完成 |
| 原文替换 | T08，与 T01 成对 | 原文改为 45 天后，答案与引用改变，不沿用 30 天 |
| 新增冲突改变动作 | T09，与 T01 成对 | 同一问题增加 D02 后，动作及状态改变 |
| 执行上限 | T10 | 决策预算为 1 时明确以 `step_limit` 终止 |

自动断言检查状态、关键词、引用、步骤、退出状态及部分行为；“引用是否语义上支持结论”“是否暗示已经裁决冲突”仍需人工复核。只满足关键词或引用子串检查，不等于所有语义要求已满足。

## 交付与复现要求

所有代码、合成资料、测试、输入、实际输出、Trace 和文档放在同一仓库。每个验收运行保留失败，不覆盖既有证据。README 应提供可复制命令，评估文档指向实际结果文件。

提交时仍必须提供题号、GitHub URL 和最终 commit SHA；私有仓库需要指定评审账号可读。目前不能把本地项目创建等同于 GitHub 发布完成，远程仓库和最终 SHA 以最终交付说明为准。不得提交真实密钥或隐私数据。

实际用时、最终测试结果及未完成部分由最终评估记录说明，不以原定投入预算替代真实耗时。
